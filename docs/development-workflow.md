# Wuji 分阶段开发与验收流程

本指南把仓库级 [协作约定](../AGENTS.md) 落成每个阶段都能执行和审计的流程。阶段工作只在已授权范围内进行非破坏性验证；不得破坏目标数据、在目标建立持久化或越权扩散。密钥、会话凭据、原始敏感证据和本机配置不得进入 Git、子代理任务书或普通报告。

## 角色与并发

- 主代理负责架构决策、阶段 Spec 和 Plan、任务拆分、公共契约的唯一归属、集成审查与最终验收。主代理保持当前模型选择。
- 开发代理固定使用 `gpt-5.6-sol`、`reasoning_effort=xhigh`，在分配的 worktree 内提交实现和本地检查结果。
- 独立测试代理固定使用 `gpt-5.6-sol`、`reasoning_effort=high`，针对 Spec 和指定提交独立取证；不能只重复实现逻辑，也不能擅自修复产品代码。
- 默认最多同时运行两个开发代理和一个测试代理。只有互不依赖、写入范围不重叠的任务可以并行；有依赖的任务按顺序执行。
- 指定模型不可用时停止对应任务并如实报告，不静默换模型。子代理不得继续拆分代理或扩大任务范围。

## 阶段文档与状态

每个阶段在 `docs/stages/<stage>/` 维护 `spec.md`、`plan.md` 和 `acceptance.md`，从 [`_templates`](stages/_templates/) 复制后填写。状态必须反映事实：

| 文档 | 初始状态 | 状态变化条件 |
| --- | --- | --- |
| Spec | `draft` | 用户批准范围和验收标准后，主代理改为 `approved` |
| Plan | `draft` | Spec 范围和实施方案获批后改为 `approved`；开始实施时改为 `in-progress` |
| Acceptance | `not-tested` | 绑定实际被测提交并完成独立验证后记录 `passed`、`failed` 或 `partial`；只有主代理完成复核后才能把阶段结论记为 `accepted` |

同一阶段用户对 Spec 和 Plan 的一次明确批准可以对两者共同生效，不需要分别确认；批准依据应在两份文档中一致记录。缺少批准依据、测试证据或被测提交 SHA 时，不得使用 `approved`、`passed` 或 `accepted`。验收记录正文固定被测试的代码 SHA；验收文档自身的提交通过 `git log -- docs/stages/<stage>/acceptance.md` 或外部索引追溯，不在同一文档中回填自身 SHA。

## 从规划到验收

1. **规划阶段。** 主代理在应用控制的 Plan 模式中研究现状并形成具体 Spec / Plan。Plan 模式不写仓库、不执行实现，也不声称自行切换了模式。下一阶段草案不授权该阶段业务开发。
2. **批准与落盘。** 用户批准后进入执行模式，主代理从模板建立阶段文档，记录批准依据、范围、非目标、接口决策、依赖、任务顺序和验证入口。同一次明确批准可以同时覆盖同一阶段的 Spec 和 Plan。实质范围或接口变化由主代理更新设计并保持状态真实。
3. **建立基线。** 主代理检查工作区、忽略规则和敏感信息，记录明确基准 SHA，再创建阶段分支与任务 worktree。首次项目快照只提供可回溯基线，不能冒充已通过测试或阶段验收。
4. **分派开发。** 每份任务书都写明绝对 worktree 路径、分支、基准 SHA、对应 Spec / Plan、允许修改范围、唯一文件 owner、验证要求和交付格式。公共契约、锁文件和迁移编号必须各有唯一负责人。
5. **开发交付。** 开发代理只在自己的 worktree 和授权文件内工作，检查实际 diff 和暂存清单，以仓库本地身份提交，并回报提交 SHA、变更文件、验证结果和限制。不得重置或覆盖其他人的变更。
6. **主代理集成。** 主代理审查任务提交和文件归属，在阶段分支按依赖顺序集成并解决冲突。集成后形成唯一的候选测试 SHA；运行源码、配置或契约变化都会产生新的候选 SHA。
7. **独立验证。** 测试代理对候选 SHA 按 Spec 验证，记录环境、命令、证据以及通过、失败、未覆盖和不适用项。测试使用自建夹具、测试租户和隔离环境；真实模型网关仅限已授权数据与预算。
8. **修复与复测。** 失败项由主代理归因并指派唯一开发者，计划内修复沿用已有授权，不重复索要许可。任何影响运行源码、配置或验收行为的修复都要生成新 SHA，并由独立测试代理复测受影响项；旧 SHA 的结果不能转用于新 SHA。
9. **最终验收。** 主代理核对 Spec、测试 SHA、集成差异、关键契约和代表性交互证据，在 `acceptance.md` 中记录结论与未覆盖风险。证据不足的项目保持失败或未覆盖，不标记通过。

## 分支、worktree 与本地 Git

- `master` 保存阶段基线；阶段分支命名为 `codex/<stage>`，子任务分支命名为 `codex/<stage>-<task>`。
- 独立 worktree 默认放在被忽略的 `work/worktrees/`。子代理只能写任务书分配的 worktree，不能在主工作区编辑。
- 仓库使用本地身份 `Wuji Development <wuji-dev@localhost>`，不得修改全局 Git 身份。
- 执行仓库脚本时优先使用 `packageManager` 固定的 `pnpm` 入口和 `pnpm exec`。终端默认 Node 与项目版本不同时，通过该入口使用项目 Node，无需也不得为此全局切换版本。
- 提交前显式运行 `git status --short`、审查 `git diff` 与 `git diff --cached`。只暂存负责的路径，禁止盲目收录依赖、密钥、构建产物、运行产物或本机索引。
- 默认只提交到本地；未经明确要求，不配置或修改远端，不推送、发布或部署。

## CodeGraph 与文件检索

主代理使用索引前先核对 `.codegraph/` 所属工作树和新鲜度，并在集成后运行 `codegraph sync`。有当前工作树索引时，理解或定位代码优先使用 `codegraph explore`；索引无结果、失效或当前 worktree 没有 `.codegraph/` 时，记录限制并回退到 `rg` 和直接读取。

子代理不得把主工作区索引当作自己分支的现状。CodeGraph 不可用不会阻止已授权工作，但任何基于回退检索得出的范围判断都应在交付中说明。

## 变更与失败处理

计划内的可逆实施、修复、本地提交和验收沿用已有授权，不重复索要许可。若发现需要改变阶段范围、公共接口、依赖锁文件或迁移归属，主代理先更新 Spec / Plan 和负责人再实施。工具链缺失、模型不可用、下载失败、检查失败或证据不足均按实际情况记录；不得通过降级模型、关闭校验、覆盖他人变更或修改全局配置来伪造通过。
