# Wuji 分阶段开发与验收流程

本指南把仓库级 [协作约定](../AGENTS.md) 落成每个阶段都能执行和审计的流程。阶段工作只在已授权范围内进行非破坏性验证；不得破坏目标数据、在目标建立持久化或越权扩散。密钥、会话凭据、原始敏感证据和本机配置不得进入Git、任务说明或普通报告。

新阶段、上下文恢复或人员交接先读根目录 [AGENTS.md](../AGENTS.md) 和[项目背景](project-context.md)，再读当前阶段的 Spec / Plan / Acceptance。文案或小样式修改按影响阅读，遵守根规则，不重复全项目审查。`project-context.md` 负责指出当前阶段、实现状态和权威文档，AGENTS.md 负责持续协作与测试约束；阶段文档记录本阶段决策和证据，不复制整份项目历史。

## 角色与协作

- 后续规划、开发、审查与验收在当前会话连续完成，不另建开发会话。主代理独立设计整体架构，负责阶段 Spec / Plan、公共契约归属、集成与最终验收，保留应用当前模型设置。
- 按需使用子代理，不强制分派；本次指定子代理使用 `gpt-6-astra`、`reasoning_effort=low`。指定模型不可用时报告，不静默替换。子代理只执行明确分配的范围，不自行扩大任务。
- 不要求独立上下文、独立 worktree、固定并发数或另设测试代理。只有互不依赖、写入范围不重叠的任务可并行；共享数据库、API 配置、故障注入和固定端口串行操作。
- 验收依据 Spec 和实际证据，不要求由另一代理执行；自行验证按实际执行者记录，不称作独立测试。历史证据保留实际执行者、模型、SHA 和结论。

## 阶段文档与状态

每个阶段在 `docs/stages/<stage>/` 维护 `spec.md`、`plan.md` 和 `acceptance.md`，从 [`_templates`](stages/_templates/) 复制后填写。状态必须反映事实：

| 文档 | 初始状态 | 状态变化条件 |
| --- | --- | --- |
| Spec | `draft` | 用户批准范围和验收标准后，主代理改为 `approved` |
| Plan | `draft` | Spec 范围和实施方案获批后改为 `approved`；开始实施时改为 `in-progress` |
| Acceptance | `not-tested` | 绑定实际被测提交并完成规定验证后记录 `passed`、`failed` 或 `partial`；只有主代理完成复核后才能把阶段结论记为 `accepted` |

同一阶段用户对 Spec 和 Plan 的一次明确批准可以对两者共同生效，不需要分别确认；批准依据应在两份文档中一致记录。缺少批准依据、测试证据或被测提交 SHA 时，不得使用 `approved`、`passed` 或 `accepted`。验收记录正文固定被测试的代码 SHA；验收文档自身的提交通过 `git log -- docs/stages/<stage>/acceptance.md` 或外部索引追溯，不在同一文档中回填自身 SHA。 纯文档阶段以文档审查基准和 diff / 链接检查作为对应证据，业务测试保持未执行，不把文档验收写成业务能力通过。

## 从规划到验收

1. **规划阶段。** 主代理在应用控制的 Plan 模式中研究现状并形成具体 Spec / Plan。Plan 模式不写仓库、不执行实现，也不声称自行切换了模式。下一阶段草案不授权该阶段业务开发。
2. **批准与落盘。** 用户批准后进入执行模式，主代理从模板建立阶段文档，记录批准依据、范围、非目标、接口决策、依赖、任务顺序和验证入口。同一次明确批准可以同时覆盖同一阶段的 Spec 和 Plan。实质范围或接口变化由主代理更新设计并保持状态真实。
3. **建立基线。** 主代理检查工作区、忽略规则和敏感信息，记录明确基准 SHA，按需创建阶段分支或 worktree，并优先沿用现有工作树。首次项目快照只提供可回溯基线，不能冒充已通过测试或阶段验收。
4. **执行或按需分派。** 主代理可直接实施；按需分派时给出相关背景、允许修改范围和交付要求，以当前工作树事实为准，不要求专门任务书模板或独立worktree。公共契约、锁文件与迁移保持变更归属清晰。
5. **开发交付。** 执行者只在分配的工作树和授权文件内工作，检查实际 diff 和暂存清单，以仓库本地身份提交，并回报提交 SHA、变更文件、验证结果和限制。不得重置或覆盖其他人的变更。
6. **主代理集成。** 主代理审查任务提交和文件归属，在阶段分支按依赖顺序集成并解决冲突。集成后形成唯一的候选测试 SHA；运行源码、配置或契约变化都会产生新的候选 SHA。
7. **按证据验证。** 当前会话对候选 SHA 按 Spec 执行最小必要验证，记录环境、命令、证据以及通过、失败、未覆盖和不适用项。测试使用自建夹具、测试租户和隔离环境；真实模型网关仅限已授权数据与预算。
8. **修复与复测。** 失败项由主代理归因并指派唯一开发者，计划内修复沿用已有授权，不重复索要许可。任何影响运行源码、配置或验收行为的修复都要生成新 SHA，并复测受影响项；未变范围可以引用原 SHA 的证据并说明不受影响依据，但不能冒称新 SHA 的实测；不因 SHA 改变而重跑全套。
9. **最终验收。** 主代理核对 Spec、测试 SHA、集成差异、关键契约和代表性交互证据，在 `acceptance.md` 中记录结论与未覆盖风险。证据不足的项目保持失败或未覆盖，不标记通过。

## 分支、worktree 与本地 Git

- `master` 保存阶段基线；阶段分支命名为 `codex/<stage>`，子任务分支命名为 `codex/<stage>-<task>`。
- 按需新增的 worktree 放在被忽略的 `work/worktrees/`；不强制另建。共享工作树时明确唯一文件 owner；执行者只修改分配范围，避免影响绑定运行 SHA 的主目录。
- 仓库使用本地身份 `Wuji Development <wuji-dev@localhost>`，不得修改全局 Git 身份。
- 执行仓库脚本时优先使用 `packageManager` 固定的 `pnpm` 入口和 `pnpm exec`。终端默认 Node 与项目版本不同时，通过该入口使用项目 Node，无需也不得为此全局切换版本。
- 提交前显式运行 `git status --short`、审查 `git diff` 与 `git diff --cached`。只暂存负责的路径，禁止盲目收录依赖、密钥、构建产物、运行产物或本机索引。
- 默认只提交到本地；未经明确要求，不配置或修改远端，不推送、发布或部署。

## CodeGraph 与文件检索

主代理使用索引前先核对 `.codegraph/` 所属工作树和新鲜度，并在代码集成后同步主工作区索引；纯文档修改不重建索引。有当前工作树索引时，理解或定位代码优先使用 `codegraph explore`；索引无结果、失效或当前 worktree 没有 `.codegraph/` 时，记录限制并回退到 `rg` 和直接读取。

子代理不得把主工作区索引当作自己分支的现状。CodeGraph 不可用不会阻止已授权工作，但任何基于回退检索得出的范围判断都应在交付中说明。

## 变更与失败处理

计划内的可逆实施、修复、本地提交和验收沿用已有授权，不重复索要许可。若发现需要改变阶段范围、公共接口、依赖锁文件或迁移归属，主代理先更新 Spec / Plan 和负责人再实施。工具链缺失、模型不可用、下载失败、检查失败或证据不足均按实际情况记录；不得通过降级模型、关闭校验、覆盖他人变更或修改全局配置来伪造通过。


## 精简测试规则

执行 [AGENTS.md 的精简测试与停止条件](../AGENTS.md#精简测试与停止条件)：2026-09-11 起不设置累计检查时间预算，不以历史剩余额度阻断必要验证。仍只做最小必要检查，同类测试脚本问题最多两轮定向排查，修复仅复测受影响项，所需检查通过即停，文档和小改动不启动全套。单命令可设防卡死超时；产品Task金额预算与真实模型调用授权额度保持原约定。

阶段全量检查在集中验收窗口执行一次。测试阻塞先用最小用例定位，不能每修一次helper都重跑冻结安装、构建、所有API和Kubernetes恢复检查。后续批量任务按待测清单分批执行，模型和工具使用应用默认设置；如需子代理，遵守本次指定模型及共享测试环境串行要求。Phase 1A当前延期项见[清单](stages/phase-1a/deferred-tests.md)。
