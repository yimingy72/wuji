## 1. 交付顺序

1. 更新主目录及本树AGENTS：同步最新架构和当前会话协作方式，保留精简测试/Git约束。
2. 落盘本批Spec/Plan及进行中的Acceptance；建立架构替代决策，列明旧决定、新决定、候选版本和实际缺口。
3. 主代理修改主架构、Harness、黑板、背景索引及活动设计入口；历史材料只加适用范围说明，不改历史证据。
4. 清理开发流程与通用模板，给旧0.5草案加显著superseded说明。
5. 一次文档一致性/链接/diff检查，修复直接发现的问题；记录实际结果与提交基准，显式暂存文档并本地提交。
6. 主目录同步规则和导航，保留原运行HEAD及未提交状态；不执行代码索引重建或服务切换。

## 2. 框架复用和设计边界

复用Cairn探索调度和原生图模型、Pi Harness与LiteLLM预算能力；补充Bridge、执行准入、真实AgentRun身份、持久结果回写、快照工具及Artifact关系。本批只记录这些接口职责，不编造已实现的Kubernetes后端、网关或工具。

单一正文分工：架构替代决策记录取舍与新增缺口；主架构描述全局边界；Harness文档描述平台侧执行/工具/模型；黑板文档描述绑定、写入和图来源；后续开发顺序由开工准备文档维护。互相引用，避免在多个正文维护不同的接口定义。

## 3. 修改范围与负责人

- 主代理：AGENTS、README、项目索引、架构替代决策、主架构、Harness/黑板正文、开工准备、本阶段三份文档；对场景、评估、参考复核及验收目录做必要的现行说明或历史标注。
- 可选文档子代理gpt-6-astra/low：只整理development-workflow、通用阶段模板与旧phase-1c-prep草案状态；不得设计架构、改业务文件或提交主代理变更。
- 本次共享已核验工作树，修改范围互不重叠；主代理统一审查并提交。使用子代理不是验收的前提，不将本次主代理检查称作独立测试。

## 4. 检查与提交

检查新增/修改Markdown的相对文件链接（忽略明确说明的占位模板），搜索活动文档中的旧框架/Token预算/强制模型规则，并人工判断历史上下文。执行git diff --check、git diff --stat和显式文件清单核对；本批不新增测试脚本，不运行安装、构建、浏览器或Kubernetes检查。

Acceptance记录文档检查实际结果、命令退出码、起始SHA、候选文档提交及限制；如记录在后续提交完成，区分被检查的文档SHA与报告提交。原P0验收与共享预算不重写。
