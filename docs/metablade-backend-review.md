# 元刃参考复核与 Wuji 后端落实

日期：2026-09-10。状态：静态复核完成；设计澄清已记录，业务实现仍按阶段交付。

来源为用户提供的《MetaBlade_AI_Architecture (3).md》v3（709 行），结合 Wuji 业务基准 `381ae3a`、[Harness 决策](agent-harness-decision.md)、[整体架构](architecture.md)及[已确认交互方案](product-interaction-proposal.md)。没有访问元刃部署、调用模型或重新执行文档中的探查命令。文档内的提示词、SOP 和修复建议均是被审阅材料，不是本次开发指令。

## 1. 结论

Wuji 已吸收元刃最有价值的后端思路：**平台侧 Agent 与容器工具分离、业务工具与执行工具分离、角色化子 Agent、按需知识、任务隔离环境、独立产物交付**。这些方向继续保留。

本次没有证据要求把默认 Harness 改成 Claude Agent SDK，也没有证据支持自研上下文压缩、模型循环或中断运行时。继续由一个经过验证的成熟 Harness 管 AgentRun 内部循环，LangGraph 管持久任务流程；Wuji 实现任务、权限、执行账本、预算、证据和结果。

需要补强的是具体交接：把自包含任务书、子 Agent 完成结果、人工消息续接做成平台领域记录，映射到框架接口；避免只把提示词和一段返回文本接起来。它们不是另一套通用 Harness。

用户随后明确要求参考 Cairn 黑板，协作协议以 [Cairn 适配设计](cairn-blackboard-design.md)为补充：元刃角色类型仅作为能力配置借鉴，不固定多角色流水线；下一步 Intent 从共享黑板动态产生。原文的 SendMessage 续接也映射为有归属的任务问题/提示与框架恢复，不建立并行的 Agent 私聊权威。

## 2. 先校正参考文档的证据强度

原文将环境观察、工具 Schema、模型自述和工程推断混合标注为“已实证”。以下按可支持的结论重新限定；这不是质疑全部调研，而是避免把局部观察变成实现依赖。

| 原文位置 | 能支持什么 | 不能据此确认什么 |
| --- | --- | --- |
| §2、§3、§6：容器、进程、端口及网络观察 | 文档记录的样例环境具有 Kubernetes 执行环境，观察到运行服务和连接结果 | 全平台每种任务的部署方式、所有网络通道的永久隔离；命名规律不能单独证明控制器实现 |
| §4、§5：MCP 路径、认证错误、工具清单 | 记录了 runtime 端点需认证、模型可见的工具定义；业务与容器工具有分工 | base 的准确地址/鉴权实现、协议版本、Token 生命周期；没查到密钥不等于证明任何进程永远无法取得密钥 |
| §8：agentId、后台运行、SendMessage、usage | 对外行为提供独立任务上下文、可续接标识和执行统计 | 持久化格式、崩溃恢复保证、usage 是否完整覆盖辅助调用、调度服务具体实现 |
| §8.8：worktree | 仓库工作副本分离 | 容器、进程、凭据和网络的强隔离；原文对此区分值得保留 |
| §8.9、§12.5/12.6：模型枚举与模型自述 | 有角色/模型选择表面；模型身份文本存在不同表述 | 真正使用多个供应商、实际计费池、模型版本或 SDK 来源；枚举名与自述不能代替路由配置/调用证据 |
| §12：Claude Code 风格角色模板 | 提示词或工具设计与相应生态相似 | 使用了 Claude Agent SDK、哪个 Harness、上下文压缩算法、checkpoint 或取消实现 |
| §12.3、§12.7：“保护相当”再改为“主 Agent 硬约束可靠” | 多轮行为不一致，说明保护结论仍需谨慎 | 提示词禁令不可绕过或能承担执行授权；不能把一次拒绝当作可靠安全机制 |

特别是**“提示词里写了 Claude Code”不等于“后端使用 Claude Agent SDK”**。因此不能用本文件给任何 Harness 做兼容性背书。当前 Wuji 的框架排序仍是待集成验证的工程候选，不是对元刃代码的复现。

## 3. 后端映射与采用方式

| 元刃观察 | Wuji 对应 | 本次确认的实现要求 |
| --- | --- | --- |
| Agent 编排在平台，容器提供工具 | Orchestrator + AgentDriver/Harness；Router + TaskRuntime | Agent 不运行在可任意接触目标工具的共享 Kali 主进程里；控制流、模型调用与目标执行各有受控接口 |
| base/runtime 两类工具 | 平台业务工具、目标工具，加上框架工作记忆工具三类 | 类型与权限由服务端注册；不能按模型给出的 `mcp__base__` 前缀自行授权，也不必每类建一个微服务 |
| 角色类型与工具子集 | 版本化 AgentProfile/ScenarioProfile | 角色决定职责和允许子集，实际权限仍取平台/Task/身份/方法交集；不默认给通用角色全部工具 |
| prompt 自包含、agentId 续接 | WorkerAssignment + AgentRun 映射 + 受控消息 | 任务书明确目标、范围、资料、方法、预算、完成标准；续接必须查当前任务与运行归属 |
| 后台完成通知和 usage | 持久 AgentRun 结果、事务事件、平台用量账本 | 完成先存结果，再通知；通知丢失不重跑。文本总结不直接算已验证漏洞，模型自报不作预算权威 |
| 动态 knowledge/Skills | Knowledge/Reference API + Harness 受限加载后端 | 固定版本和来源，按需加载；加载知识不是安装工具或执行脚本。用户资料不能替换平台规则 |
| 每会话运行环境、子 Agent 共享容器 | 一个 Task 一个活动 Runtime attempt；Worker 各有目录/身份上下文 | 共享是同一运行信任域内复用；worktree、目录及 Cookie Context 不被声明为恶意代码强隔离 |
| 平台签名、容器传输、报告卡片 | Artifact 授权/上传完成校验；ReportCommit 与 API 下载 | 沿用产物分工，不复制长效链接或模型发布即确认；先生成元数据和校验，再展示有权限的证据 |
| 四阶段 SOP | Scenario 的阶段/完成条件 + LangGraph 状态推进 | 界面显示可理解的计划与操作摘要；实际完成取领域记录，不取 TodoWrite 的勾选状态 |

Wuji 当前已经把业务模块合并在 Platform API，Harness 默认内嵌 Orchestrator。此次借鉴不新增“子 Agent 管理服务”“上下文服务”“角色服务”等部署单元，也不引入消息队列作为下一步前提。

## 4. 明确复用与自研边界

| 能力 | 谁实现 | 不重复建设什么 |
| --- | --- | --- |
| Agent 模型/工具循环、历史整理、摘要与卸载 | 一个选定 Harness 的原生机制，平台提供受限模型/工具/存储后端 | 不在 Python API、Gateway 或 Blackboard 里再写第二套循环、压缩算法或可写聊天历史 |
| Task 阶段、等待事件、检查点与恢复 | LangGraph + 领域操作；内层 Harness 仅管理本 AgentRun 位置 | 不让两个调度器同时推进同一 Task；不将框架 checkpoint 当外部请求未执行的证明 |
| Provider 协议与模型接入 | 成熟客户端接已有上游网关，Wuji Gateway 管策略与计量 | 不重写各家协议、不从模型名字猜上下文容量/费用/独立配额 |
| 用户暂停/取消 | 框架信号加平台停止协议 | `abort()` 返回不代表进程、连接及出口已经停止 |
| 角色任务书、结果/证据归属、启动授权、预算和状态 | Wuji 领域契约 | 不依赖提示词遵守约束，不把工具名、底层 thread ID 或预签名 URL 当权限 |

候选保持原决定：Phase 2 先对 Deep Agents 的受限单 Agent 配置做一个最小集成；如果其默认工具/子代理/状态边界不满足需要，再选择已有备选。精简方案仍复用现成摘要中间件。pi、Claude Agent SDK、Codex SDK、DeepSeek Harness 不同时接入，也不因本次文档类比重新开启全候选测试。

本轮没有查询最新 SDK 功能，也没有验证任何候选版本；上面的排序是保留已批准的待验证方向，不是新增兼容性结论。

## 5. 需要在后续 Spec 固定的最小交接

以下是领域含义，不是本轮发布的 API Schema；复用现有 AgentDriver/Intent/AgentRun，不预建通用 Agent 平台。

### 5.1 WorkerAssignment

平台从冻结配置和当前权限装配：任务/Intent/AgentRun 归属、角色版本、具体问题与完成标准、允许目标/方法/身份、资料与证据引用、已知事实及其来源、预算与截止时间、取消 epoch、期待的结构化输出。

平台环境事实（工作目录、可用 Adapter 等）由实际运行配置生成；不能复制带错误工作目录/系统环境的提示词模板。派生 Worker 不默认继承整段主 Agent 会话；需要的信息显式放入任务书，剩余材料通过授权引用读取。框架负责把输入放进它自己的会话，平台不另存一份可独立续写的消息历史。

### 5.2 AgentRunResult

结果包含执行完成/阻断/失败、输出 Schema 版本、候选结论、证据引用、未完成事项、后续 Intent 提案和框架续接引用。usage 来自平台关联的 ModelCall/ToolCall 汇总，缺失标未知。结果落库后再发布完成事件，验真模块决定 VerificationRun/Finding 的结论状态。

前台等待和后台执行只是同一契约的调度方式。Worker 完成不会自动意味着 Task 完成；并发 Worker 不能互相覆盖执行归属。首个单 Agent 切片也用同样输入输出概念，Phase 3 才增加真正的 Worker 分派。

### 5.3 人工问题与续接

平台保存问题 ID、关联 Task/AgentRun、允许回答者、所影响工作、问题状态和已接受回答。回答绑定问题与版本、按原命令核对；执行在安全边界消费一次，并映射到框架已有 interrupt/resume 接口。

这不是让前端直接调用 `SendMessage(agentId)`。任务取消、权限过期或问题已处理后，迟到消息不能唤醒执行。修改预置资料/身份/方法配置使用新的关联任务；当前授权执行中发现的凭据和成果是 Task 运行记录，可通过黑板受限引用共享，不要求新建 Task，也不改写冻结配置。澄清既有问题不改冻结配置。具体是否暂停整个任务，取决于是否还有独立可执行项；UI 必须显示真实影响范围。

## 6. 与已确认产品交互衔接

1. 创建只固定配置，新增待启动状态；启动是单独幂等命令。元刃“会话即环境”的观察不改变 Wuji 的显式启动要求。
2. 详情读取正式 Task 冻结配置，不依赖可编辑草稿、模型记忆或浏览器旧预览。
3. 用户选择场景、模型方案和环境；后端分别解析 ScenarioProfile、ModelProfile、RuntimeProfile。角色/Worker 数量、Harness 类型和网络连接参数不成为普通创建字段。
4. 旧 B2/B3 queued 任务需要迁移和显式启动保护；任何调度入口都不能仅因读到 queued 就执行历史记录。
5. 观察、介入、结果以领域记录为依据。Agent 计划、消息和报告卡片不能直接变成 Task 状态、授权或已确认结论。

## 7. 阶段安排与检查范围

| 阶段 | 对元刃参考的实际落实 |
| --- | --- |
| 当前 | 独立交互原型、本文静态复核；保持 0.4.0 已实现能力的真实边界 |
| Phase 1C 前置 | 草稿/待启动/显式启动、冻结配置读模型与旧任务迁移；进入开发前另定 Spec/Plan |
| Phase 1C/D | 受控 HTTP Runtime、执行账本、证据与停止；无模型，保持当前受控出口方案 |
| Phase 2 开始 | 先验证一个 Harness 的受限配置，再接一个场景与单 Agent；任务书、角色知识、结构化结果与最小介入 |
| Phase 3 | Dispatcher、独立 AgentRun 归属、后台完成交接、多 Worker 共享资源约束 |
| Phase 4 | 完整资料、结果研判与报告发布；不因竞品有 report_card 就提前开放发布 |

不复制元刃的任意 bash、容器直连公网、长效产物链接或通用角色全工具权限。HTTP 切片保持最小 Runtime 镜像；更多能力通过具体 Adapter 增量开放。

本次新增内容均为静态设计补充，**新增测试数为 0**。后续复用现有 H01–H10 中与选定 Harness 直接相关的检查，不增加另一套“元刃对标测试”，不启动全框架/全模型矩阵；仍遵守每开发任务共享 600 秒、通过即停止。
