## 1. 设计依据与取舍

用户的核心任务是：说明想验证什么，选择已授权对象，以可控的成本执行，看懂发生了什么，在必要时介入，最后取得有依据的结果。

沿用已认可的 Ant Design 工作台、紧凑布局与五套主题（silver 默认、glacier、celadon、slate、graphite）。本轮调整信息结构和操作语义，不重新选框架或另做视觉系统。

| 依据 | 值得借鉴 | Wuji 的具体取舍 |
| --- | --- | --- |
| 衍迹调研 §4.2：先选场景，有“创建并启动”入口 | 先理解作业，再填写参数 | 场景决定所需输入和完成标准；明确保存草稿、创建、启动三种动作 |
| §4.4、§5：时间线、工作区、证据关联 | 执行与证据相互定位 | 先做好时间线与单条证据链；全图和历史回放后置 |
| §10：资料源与任务关联 | 资料参与任务，避免重复输入 | 选择可用资料版本；不让用户填写引用 ID 或特殊提示词语法 |
| §11、§12：Runner、模型配置独立管理 | 配置复用，任务只做选择 | 任务选逻辑模型方案和执行环境，管理员管理 Provider、密钥、集群与配额 |

## 2. 完整作业流程与页面结构

```text
项目 / 任务列表
  └─ 新建任务：场景与目标 → 对象与范围 → 运行配置 → 确认任务
       ├─ 保存草稿 → 稍后继续填写
       └─ 创建任务 → 待启动详情 → 启动
                                     ↓
                          排队 → 准备环境 → 执行观察
                                              ↕
                                回答问题 / 处理阻断 / 暂停恢复
                                              ↓
                              结果：结论、覆盖、证据、限制
                                              └─ 复测：创建有关联的新任务
```

任务列表是持续工作的入口；详情是同一个任务从待启动到结束的连续空间，不能运行时只看聊天、结束后另找结果。详情保留返回列表时的筛选、分页和所选项目。

桌面详情采用可收起的三栏：左侧任务上下文与计划，中间当前工作及时间线，右侧所选记录的证据。顶部固定任务状态与当前可用动作；预算、待处理事项和清理状态各自显示，不挤成一个进度百分比。较窄窗口将证据改为抽屉/下方区域。

完整产品导航保留“作业”和“配置”分组。任务内优先提供结果、证据和资料的上下文入口；资产、报告、资料库、模型等全局模块在可用后才进入主导航。首批不展示一排不可用菜单。

## 3. 创建任务：四步而非参数表

### 3.1 总体规则

- 四步向导使用普通页面，保留上下文；不放进大型弹窗。顶部可回到已完成步骤，右侧/底部显示简短任务摘要。
- 默认只要求用户明确**场景、想验证什么、测试对象**，再处理当前任务真正缺少的条件。任务名称自动建议，可编辑。
- 按场景裁剪内容：首批只有 HTTP 观察时显示已选场景摘要，不要求在单张卡片上再点一次；没有资料、身份和模型能力时，第三步仅呈现环境与预算摘要，不展示空表单。
- 页面使用“测试对象、使用哪个身份、运行多久”等语言；内部 ID、摘要、权限版本、幂等键不成为表单字段。
- 系统自动识别的 URL、推荐范围或预算必须可见；从自然语言提取的对象需要用户确认，不能偷偷变成授权目标。
- 后退、主题切换保留当前输入。切换场景保留通用内容，对不兼容配置提示移除，不静默携带凭据或扩大测试范围。
- 保存草稿不等于提交命令。默认不把目标、提示词、资料正文和凭据写入 localStorage/sessionStorage；正式草稿由服务端按权限保存。

| 步骤 | 用户需要填写/确认 | 系统默认 | 高级配置或条件显示 |
| --- | --- | --- | --- |
| 1. 场景与目标 | 选可用场景；确认目标描述 | 按场景提供可编辑目标、完成标准及任务名称建议 | 自定义成功条件、明确不做的事项；方法限制只在场景支持时显示 |
| 2. 对象与范围 | 输入对象或选择已有资产；确认授权范围 | 当前项目；只有一个适用授权时预选；显示排除项和到期时间 | 缩小到路径/对象子集；多对象仅在支持的场景开放 |
| 3. 运行配置 | 处理必需资料/身份/环境缺失，其余可沿用默认 | 匿名或场景要求的身份；项目模型与环境；保守预算 | 单任务覆盖可授权的模型方案、环境、预算明细；不允许超出项目限制 |
| 4. 确认任务 | 阅读“将做什么、使用什么、最多消耗多少”；创建 | 展示服务端预览与阻断原因 | 返回对应步骤修改；不再塞入新的技术字段 |

### 3.2 第一步：场景与目标

场景是带输入要求、方法边界和完成标准的作业模板，不只是装饰标签。卡片显示一句“适合做什么”、必需输入和当前可用能力。生产环境只列出可用场景；完整路线图放在帮助/规划中，避免出现大量不可点击的卡片。

| 场景方向 | 用户目标示例 | 必需输入 | 开放边界 |
| --- | --- | --- | --- |
| HTTP 观察 | 查看指定入口的响应、配置和公开内容 | 一个 URL、已授权范围 | Phase 1C/D；固定受控方法，无 Agent |
| Web 观察评估 | 梳理入口公开信息，记录有依据的风险线索和未覆盖项 | URL、明确目标、授权范围、可用模型方案 | Phase 2 第一个内置 Agent 场景；不能标成全面渗透 |
| Web/API 专项验证 | 在指定测试身份下核对某项行为或已有风险线索 | 对象、验证问题；按方法要求提供接口资料和测试身份 | 对应 Adapter、身份管理与验证方法具备后开放；不默认允许写目标数据 |
| 代码审查 | 审查固定源码快照中的指定问题 | 已处理的源码/资料版本、关注点 | 后续只读代码能力；不自动安装依赖或执行仓库脚本 |
| 多资产评估 | 对选定授权资产执行同一明确评估计划 | 资产集合、逐项授权、分配预算 | 多资产与调度能力交付后开放 |

“复测”是从既有结果发起新任务的快捷方式，不另造一套生命周期。“自定义”后续允许组合已支持的方法，不等于开放任意命令、任意工具或任意目标。CTF、攻防演练等名称不直接照搬到首批业务入口。

目标输入以“希望得到什么结果”为主，示例：“查看 https://app.example.test 的响应配置和公开内容，列出证据与未检查部分。”名称可自动生成“app.example.test · HTTP 观察”。纯 HTTP 首批提供固定、可确认的观察目标，不假装自然语言会驱动规划；Agent 阶段才允许目标影响执行计划。

场景模板给出初始完成标准，用户可以增加关注点。自由文本不能赋予新的工具权限或扩大授权。未知的覆盖范围要标为未知，不能预先承诺“全站检查完成”。

### 3.3 第二步：测试对象与授权范围

默认入口是粘贴 URL；资产库具备后增加“从项目资产选择”，两者产生同一种可见对象列表。资产发现、资产登记和目标授权是三件事：已有资产也必须满足有效授权，运行中发现的新对象不能自动加入可访问范围。

对象确认区显示：规范化地址、可访问部分、明确排除部分、使用的授权名称/版本和到期时间。URL 内有凭据时提示改用身份配置；不把含密钥的地址直接保存或展示为普通任务名称。

- 一个适用授权：预选并展示，用户仍可查看具体范围。
- 多个适用授权：由用户选择，不悄悄合并成更宽范围。
- 无适用授权或对象超范围：指出具体对象和缺失条件；保留输入，可保存草稿。Operator 不能在创建页直接扩权；有权限者通过授权管理处理后回来重新预览。
- 用户缩小范围：使用包含路径/对象和排除项等产品表达；不能解除上级限制。
- 授权过期或执行中变更：启动/继续前重新核验；执行侧仍按当前有效策略约束，不能因创建时通过就永久有效。
- 源码等离线场景按资料访问授权和允许方法检查；不能强行要求填写没有意义的网络目标 URL。

创建预览检查配置、授权和范围，不进行目标探测、模型推理、DNS/网络可达性测试或隐式资料下载。执行环境显示的是平台已知健康状态；目标是否可达由明确启动后的受控操作验证。

### 3.4 第三步：运行配置

本步分为“资料与身份”“模型与环境”“预算”三个可折叠区。每区先显示所选配置摘要，只有缺失项或用户展开时才出现表单。

| 配置 | 默认与普通交互 | 必填条件 | 高级/管理入口 |
| --- | --- | --- | --- |
| 资料 | 无资料也可进行公开 HTTP 观察；从项目资料选择固定版本 | 代码场景需要源码快照；接口专项按方法要求提供定义 | 上传处理、来源、版本、更新时间与访问范围；Git 拉取属于独立导入任务，不在创建时暗中执行 |
| 测试身份 | 默认匿名；显示身份名称、用途和有效性，不显示 Secret | 验证登录态或身份差异的方法才要求相应测试身份 | 身份管理负责录入/轮换；角色对比明确选择各身份，不能隐式复用操作者的平台登录态 |
| 模型方案 | Agent 场景沿用项目已配置方案，展示名称及数据处理约束 | Agent 场景需要可用方案；HTTP 观察没有模型字段 | 有权用户可换已发布方案；Provider、Base URL、API key、重试/压缩/Harness 放配置中心 |
| 执行环境 | 默认项目受管环境；本地为现有 Kubernetes 对应的环境配置 | 需具备场景要求的 Adapter、出口和资源能力 | 选择已授权环境/出口位置；不填写 namespace、镜像、Pod、shell 或自建代理参数 |
| 预算 | 展示预设的时间和请求上限；Agent 增加模型额度 | 所有执行任务都需有上限 | 展开请求速率、并发、单次超时、响应大小、Token 上限等；上限受项目/租户约束 |

资料必须处理完成且当前用户可读才可选用；选择时固定内容版本。任务输入与资料是待解释的数据，不是提升权限的指令。身份只保存逻辑引用，密钥不进入任务 DTO、提示词或浏览器缓存；可用性不能通过未经用户启动的目标请求来“测试”。

环境不可用需要区分“配置不兼容”和“暂时繁忙”：缺 Adapter 属于配置阻断；已配置环境暂时离线/无容量允许保存或创建完整任务，但不能显示可立即运行。不能只因本地 Kubernetes 存在就认定执行环境已经就绪。

首批 HTTP 预算摘要沿用现有预览默认值作为候选：最多 60 秒、20 次目标请求，详细项为 1 RPS、并发 1、单次 10 秒、响应 1 MiB。这是现有配置值，不是已实测的运行保证；Phase 1C Spec 需确认计量口径与默认值。单 URL 观察不会为用满预算而重复请求。

Agent 场景建议默认“项目标准预算”，展示具体上限，避免“经济/平衡/极速”标签没有定义。模型重试、回退与子 Agent 共用任务总额度。只在价格版本与计费机制可靠时显示金额估算及金额上限；否则显示 Token/调用额度，费用标为暂不可估算，不能写成零元或承诺固定总价。

### 3.5 第四步：确认任务

确认页展示一张可读的作业摘要：

> HTTP 观察 · app.example.test
>
> 目标：记录入口响应配置和公开内容。
>
> 对象：1 个 URL；授权：项目测试范围；排除项：展开查看。
>
> 方法：受控 GET；身份：匿名；资料：无。
>
> 环境：项目默认环境；预算：最多 60 秒 / 20 次请求。
>
> 结果：响应记录、证据和未完成原因。
>
> 创建后状态：待启动。

每项可返回对应步骤修改。显示“可以创建”与“暂不能启动”的不同原因，例如配置完整但执行环境离线。完整性/授权检查不通过则禁用创建，提供到具体字段的修复入口；保存草稿仍可用。

预览是短期校验结果，不是执行许可。影响任务语义的输入变化后使旧预览失效；原有待确认命令仍按原键核对，不能靠刷新预览掩盖提交结果不明。

## 4. 保存、创建、启动：明确三种承诺

| 动作 | 用户得到什么 | 不会发生什么 | 失败后的交互 |
| --- | --- | --- | --- |
| 保存草稿 | 可继续修改的未完成配置，显示保存时间 | 不产生执行任务、不排队、不调用目标或模型 | 保留内存输入，提示重试；离开页面前可选择保存或放弃 |
| 创建任务 | 一个有 ID、配置固定、可查看/取消的“待启动”任务 | 不创建 Runtime、不排队执行、不消耗执行预算 | 结果不明按原键核对；刷新后只读恢复，不猜测新建 |
| 启动任务 | 接受执行意图后进入排队，随后准备环境和执行 | 不把 HTTP 202 当作已开始运行 | 校验失败留在待启动并给原因；结果不明核对原启动命令，不换键 |

建议正式任务新增 `ready`，用户文案“待启动”；`queued` 只表示已接受启动、等待执行。草稿独立于 Task 生命周期：

```text
可编辑草稿 --创建--> ready（待启动） --启动--> queued（排队中）
                                                ↓
                                    provisioning → running → …
ready / 从未执行的 queued --取消--> cancelled
运行后取消继续采用 cancelling → 停止核实 → cancelled，清理状态单列
```

正式任务的配置快照固定。“编辑任务”仅针对草稿；待启动任务有改动需求时使用“基于此任务调整”，生成新草稿再创建新任务，原任务可取消。执行中的补充回答只能澄清既有目标；增加资料版本、变更身份/方法等影响方法依据的配置需创建有关联的新任务。Scope 变更仍按架构规定走有权限的版本变更与执行隔离流程。

启动必须重新检查当前操作者权限、授权有效性、配置版本是否被撤销、环境能力与预算，原子防止重复派发。启动按钮的可用性来自服务端能力与当前状态，Viewer 不因能看到详情而获得执行权限。

**建议首批不提供“创建并启动”。** 完整产品可将其作为用户主动选择的快捷动作，但必须组合两个可恢复的命令：先创建，再启动。启动失败保留已创建任务并定位失败原因；刷新后不自动补发启动。页面分别显示命令结果，不能把创建成功误报为执行已开始。

### 4.1 草稿和命令恢复分别处理

- 草稿保存配置；提交恢复记录只保存当前用户/项目、命令种类、幂等键、资源 ID 和时间。两者不能互相替代。
- 首次交付草稿采用显式“保存草稿”，默认仅创建者在仍有项目权限时可读写；团队共享另行设计。保存使用版本检查处理多标签页覆盖，无需先做自动保存和多人协作；后续自动保存需明确保存状态。
- 当前项目同一时刻一个待确认命令的约束继续保留。未确认时可核对或主动查看列表并确认放弃核对，不能自动开启第二个写流程。
- 刷新后回执查询 404 仍为“提交结果待确认”，不推断失败，不自动重建任务或启动。
- 项目切换、退出或身份变化时，草稿访问、待确认记录与迟到响应都按归属隔离；输入有未保存修改时先给离开提示。

## 5. 执行观察：看当前工作，而非看内部框架

任务详情的首屏回答：现在是什么状态、正在处理什么对象、已经完成哪些计划内工作、哪些需要我处理、目前消耗多少。

| 区域 | 呈现内容 | 交互 |
| --- | --- | --- |
| 顶部状态条 | 状态、当前阶段、执行耗时、预算使用、环境/清理状态 | 仅展示当前可用的启动、暂停、恢复、取消；命令接受后读取真实状态 |
| 左侧任务上下文 | 目标、对象、授权、配置摘要；Agent 阶段增加计划与覆盖项 | 点选对象/计划项过滤记录；查看创建快照与授权变更历史 |
| 中间执行区 | 按时间的操作摘要、结果、计划变更及待处理事项 | 展开单条请求/工具记录，跳到证据；不显示模型隐藏推理或假角色协作 |
| 右侧证据区 | 所选操作对应的响应/文件/截图等原始依据与来源 | 脱敏展示、按权限查看/下载；证据类型决定展示方式 |

执行进度、覆盖率、风险结论、资源回收分别呈现。没有固定总工作量时只显示阶段和已完成数量；有覆盖计划时写“已评估 3/5 项计划”，并标明阻断/未评估，不写“全站安全检查 60%”。

连接中断时显示“状态同步中/上次更新”，保留已确认的只读数据并允许重试；不能把前端断线显示成任务已停止。事件用于触发权威快照刷新；首批复用已有有界轮询，不为交互改版另行引入消息队列或要求 SSE。执行未知结果与业务结论不明确使用不同提示。

终态时让结果成为默认内容，但保留时间线。历史回放只读取已存记录；“再执行/复测”是明确的新任务，不复用回放按钮向目标发请求。

## 6. 人工介入：按问题给动作

人工介入以任务内的待处理卡片为中心。卡片包含发生什么、哪些工作受影响、推荐动作、所需权限和处理后会发生什么。普通聊天消息不能替代状态变更命令，也不能绕过 Scope 与预算。

| 情况 | 用户动作 | 系统行为与边界 |
| --- | --- | --- |
| Agent 需要解释目标 | 在问题卡回答或跳过该项 | 记录回答来源；只能澄清现有目标，不提升工具权限或改配置版本 |
| 需要新的资料/身份/方法 | 查看缺少什么，基于当前任务调整并创建关联任务 | 原任务保留已有证据和未完成原因；不静默替换冻结配置 |
| 授权过期或对象超出范围 | 查看受阻对象；有权者更新授权，其余人联系有权角色 | 新授权版本经过受控生效，再显式继续；不能通过“继续”按钮直接扩权 |
| 达到预算 | 查看已用额度和未完成工作；首批结束或创建后续任务。完整产品中有权限者打开“调整额度”，查看已用/剩余/项目可分配额度，输入新增上限与原因 | 不自动追加预算；增额记录为独立变更，不改原配置快照，成功后仍需显式恢复。需预算预占与变更契约交付后才开放 |
| 用户希望暂缓 | 暂停；停止条件达成后显示已暂停 | 前端关闭流式显示不等于暂停执行；恢复重新校验 |
| 用户要求停止 | 取消任务 | 展示取消中、已停止与清理结果；保留已产生证据，不承诺撤销已发请求 |
| 调用结果未知 | 查看已知记录，等待系统核对；在能力具备后采用明确的处置动作 | 不允许用户简单点“标记成功”绕过执行账本，也不自动重复调用 |
| 结果需要人工研判 | 对具体结论及证据进行确认/退回并填写依据 | Phase 4 独立权限与审计；不修改原始证据 |

首批 HTTP 闭环仅开放启动、取消、错误查看及证据检查。暂停/恢复、问题回答、授权在途变更等只有对应后端状态契约交付后才显示。全产品原型可以演示这些场景，但必须注明规划能力。

## 7. 查看结果：过程、结论与报告分层

结果页依次提供：

1. **结果摘要**：任务完成/取消/失败的原因；实际完成的工作。Phase 1 叫“观察结果”，不能包装成 Agent 漏洞报告。
2. **覆盖与限制**：纳入计划的对象/维度、已评估项、受阻和未评估项、有效身份、授权版本及预算停止原因。
3. **发现与验证**：观察事实与风险候选分开；证实、未复现、不明确是验证结论，不与执行失败混用。
4. **证据与追溯**：从结论跳到验证记录、原始证据和执行上下文；按类型渲染，不把任何文件伪装成 HTTP 流量。
5. **下一步**：对未完成部分或具体发现发起有关联的复测任务；查看/导出当前具备的报告格式。

“未发现已证实漏洞”必须同时呈现覆盖与限制，不能替换为“安全”。停止后的清理未完成单独提示，不抹掉已取得的结果。

Phase 2 先提供固定快照的 Markdown 评估摘要；实时结果页和导出快照有明确版本/时间。完整审核、发布、整改、HTML/DOCX 等在 Phase 4；没有实现的格式不显示下载按钮。

## 8. 完整体验与首批可用范围

“首批”需要区分工具闭环与 Agent 产品。前者验证执行基础，后者才承担基于目标的自动评估；不能把 HTTP 观察宣传为完整 Agent 渗透。

| 能力 | 当前 B2/B3 | 首批真实执行：Phase 1C/D + 交互前置调整 | 首个 Agent 可用版：Phase 2 | 完整产品后续 |
| --- | --- | --- | --- | --- |
| 创建输入 | 名称、URL、Scope、GET/HEAD、六项限额 | 固定 HTTP 观察场景，简化目标确认，授权预览 | 内置 Web 观察场景、自然语言目标、完成标准 | 更多经能力验证的场景与多对象 |
| 保存/创建/启动 | 无服务端编辑草稿；创建即 queued，无执行 | 显式草稿、待启动、启动命令；先调整任务语义再接 Runtime | 复用；可评估加入创建并启动快捷操作 | 任务模板、团队草稿等按需求 |
| 资料和身份 | 无 | 匿名、无资料；相关配置不显示 | 已处理资料版本；首个公开观察仍可匿名 | 身份配置、角色对比与更多导入方式随能力交付 |
| 模型与环境 | 无执行选择 | 固定受管 HTTP 环境，不显示模型选择 | 项目逻辑模型默认值、配置快照、单 Agent | 多 Agent 及更多受管环境；不暴露实现细节 |
| 预算 | 创建时保存限额 | 请求/时间/资源额度真实约束与展示 | 增加模型总额度与可靠计量 | 受权限控制的调整及组织配额管理 |
| 观察与介入 | 列表/快照/创建取消事件 | 真实调用、证据、取消、停止和清理 | 计划/验证记录、必要问题与受控恢复 | 多 Agent 交接、复杂人工研判 |
| 结果 | queued/cancelled 状态，无执行结果 | 原始响应、操作记录、未完成原因 | 最小资产/事实/验证/覆盖与 Markdown 快照 | 关系图、Finding 工作流、多格式报告 |

本方案建议的草稿、待启动与启动语义是**新范围**，不倒填为 B2/B3 已承诺或已交付。应在用户确认交互后，作为 Phase 1C 前置小批次写入具体 Spec / Plan，再连续接入已规划的 Runtime。Phase 1A partial、master 基线及既有验收证据保持原有含义。

### 9.1 旧任务迁移必须先于调度器开放

## 10. 可点击原型制作计划（本轮不实施）

### 10.1 原型内容

方案评审通过后制作一个独立入口的高保真交互原型，复用五套主题和工作台组件。原型顶部清楚标识“交互预览”；模拟状态不能与正式 4180 工作台或真实 API 混用。

原型提供“首批 HTTP 闭环”和“完整 Agent 体验”两条明确标注的演示路径，用同一信息结构呈现，不另做两套视觉风格。

| 页面 | 可点击内容 |
| --- | --- |
| 任务列表 | 草稿/待启动/执行中/已结束样例；继续草稿、新建、查看任务 |
| 四步创建 | 选择场景、修改目标、确认对象/授权、选择资料/身份、展开预算、返回修改、查看阻断 |

| 结果 | 覆盖与限制、观察与验证依据、有关联的复测入口、报告版本示意 |
| 恢复情形 | 提交响应丢失后刷新核对；保留已创建任务；不自动再创建或再启动 |

样例使用保留示例域名和合成证据；模拟结果不是实际安全评估。不会新增完整关系图编辑器、终端、模型配置中心或全格式报告实现。

### 10.2 原型评审路径

1. 默认配置完成一次 HTTP 任务创建，清楚看到尚未启动；再启动、观察、取消并查看已收集结果。
2. 目标无有效授权，能定位问题并保存草稿；无法通过确认按钮绕过。
3. Agent 任务带资料创建，能解释选用的模型、身份、环境、预算及所需人工输入。
4. 创建已成功但启动不可用，看到已创建记录和可修复原因，不重复新建。
5. 执行中出现一个待处理问题，处理后状态和证据关系清楚；新资料/身份变更引导新任务。
6. 零已证实漏洞但有未完成项，结果不误导为目标安全；复测保留原结果关联。

这些首先是产品走查，不是要求立即建立六套端到端测试。原型只做必要构建和一次连贯页面走查；文档阶段不启动任何测试。

## 11. 评审建议与后续实施边界

建议确认以下产品决策后进入原型：

1. 四步创建；模型/环境/预算使用项目默认，高级配置收起。
2. 草稿可编辑，正式任务配置固定；创建进入待启动，启动才允许排队执行。
3. 首批提供显式创建和启动两个动作；“创建并启动”留作完整产品快捷方式。
4. 第一条真实执行是匿名 HTTP 观察；第一条 Agent 体验是 Phase 2 内置 Web 观察评估，更多场景随能力开放。
5. 同一详情空间贯穿观察、介入和结果；时间线与证据优先于全图。
6. 交互确认后把状态/草稿/启动调整列为 Phase 1C 前置批次，再继续前后端开发。

后续实施仍由主代理固定 Spec / Plan，开发使用 SOL/xhigh 独立 worktree，独立测试使用 Luna/xhigh。每个获批开发任务共享 600 秒检查预算，主流程和直接受影响边界通过即停止；不借此次交互调整重跑 Phase 1A/B 全套。文档核查仅检查差异与事实，本轮无安装、构建、浏览器测试或 Kubernetes 操作。
