本文是 2026-09-09、v0.4 设计基线上的历史复审，保留当时问题、证据范围和修正理由。“尚无平台后端”“接下来”等进度描述只适用于该次审查时点；当前实现状态以[项目背景](project-context.md)和各阶段 Acceptance 为准。设计原则仍适用，但不能把本记录当作当前阶段完成证明。

## 1. 复审结论

平台应复用成熟 Agent Harness 的上下文、压缩、模型/工具循环和打断能力，复用 LangGraph 的持久执行，并复用模型客户端及已有企业网关。Wuji 的自研重点是安全评估业务：范围、任务、执行许可、证据、预算和交付。原架构只写 LangGraph，缺少完整执行层的职责约定，容易在开发时重复实现这些基础能力。

保留 PostgreSQL 作为业务权威、Router/Runtime/Egress 三处执行约束、VerificationRun 与 AgentRun 分离、证据/报告快照以及现有前端技术栈。它们解决的是平台业务和执行问题，不能由通用 Harness 替代。无需重写已有工作台，也不把多 Agent、图数据库、CRD 或更多代理层提前变成开工前提。

## 2. 已发现并修正的问题

严重程度表示进入对应功能实现前的处理优先级，不表示发现了已部署系统漏洞。

| 编号 / 优先级 | 原设计缺口与影响 | v0.4 修正 | 验证 |
| --- | --- | --- | --- |
| R01 / P1 | 只指定 LangGraph；上下文历史、压缩、结果卸载和完整 Agent 循环没有明确复用方 | Harness 唯一管理上下文，平台只提供 ContextPolicy 和业务输入；首选验证 Deep Agents，精简方案也复用现成摘要中间件 | H01、H10 |
| R02 / P1 | Gateway 承担“消息编译”，容易与 Harness 重排历史/压缩重叠，并重复写各厂商协议 | Gateway 收敛为策略与计量边界，协议用现成客户端；不二次编排会话或改写不透明续接状态 | H06、H07 |
| R03 / P1 | 只约束主 Agent 模型调用，框架摘要、工具选择等内部请求可能绕过网关和预算 | 所有辅助模型显式注入受控客户端，标记 purpose，同 Task 预占、结算和取消 | H02 |
| R04 / P1 | 把框架打断与任务暂停/取消混用，会过早显示已停止或恢复旧会话 | 复用框架 API，平台映射 epoch、排空、断流和重新授权；用户补充指令在安全边界处理 | H03、S09–S11 |
| R05 / P1 | Graph 与业务账本分开提交，内层恢复后生成新工具 ID 仍可能重复执行 | 动作先持久化，按稳定执行位置对账模型与工具；不支持稳定恢复时停下核对；业务状态操作在 Phase 1/2 复用 | H05、A07、H10 |
| R06 / P1 | 模型 fallback 只检查策略与预算，忽略协议、工具、上下文及会话兼容性 | 路由绑定兼容信息，不兼容切换在安全边界新建会话段；模型列表、实测能力、实时健康分开 | H07 |
| R07 / P1 | 业务 RLS 不能自动覆盖框架自建表；工作记忆、卸载文件和第三方 trace 未完整纳入存储边界 | 检查点复用库实现，单独验证角色/归属/清理；框架数据继承分类与保留，第三方 tracing 默认关闭 | H08 |
| R08 / P2 | “所有工具经 Router/Runtime”混淆上下文辅助工具与目标操作，也容易误开放默认 shell | 分为框架工作记忆、平台业务工具、目标工具；各自按权限与资源边界执行，目标操作统一 Router | H04 |
| R09 / P2 | 框架流事件与持久业务 SSE 没有分层，直接转发会暴露内部协议或使 Outbox 被 Token 片段填满 | 业务语义事件持久化；未来文本片段走有界临时流，重连恢复快照及最终摘要 | H09、F06–F07 |
| R10 / P2 | 总表要求 Kali，HTTP 首个切片却只需要受信 HTTP Adapter，部署要求不一致 | TaskRuntime 按 Profile 选镜像，首版最小 HTTP 镜像，后续按需求接 Kali；保留既定 Kubernetes 与出口边界 | S01、S16 |

修正位置见 [主架构第 3、5、7–10、13 节](architecture.md)、[Harness 决策](agent-harness-decision.md)、[评估模型](assessment-model.md) 和 [前端事件边界](frontend-architecture.md)。在本次复审时点，新增 H01–H10 后形成的 80 项平台验收场景尚无整体验收结果。

## 3. 复用与自研清单

| 部分 | 复用 | Wuji 实现 |
| --- | --- | --- |
| Agent | 现成 Harness、上下文与压缩机制 | 一种默认实现的薄适配、领域输入输出、受控工具绑定 |
| 编排 | LangGraph/checkpointer 的执行、保存与恢复能力 | Task 阶段、版本、租约、跨账本核对与幂等边界 |
| 多模型 | Provider SDK/模型客户端、用户已有网关 | 能力/路由策略、调用身份、预算与用量对账 |
| 工具通信 | MCP 协议实现及结构化 Schema 工具 | Scope 校验、执行账本、许可、受限 Adapter 和出口策略 |
| 存储与集群 | PostgreSQL、S3 客户端、Kubernetes API/CNI 能力 | 领域 Schema、控制器协调、隔离配置和资源清理 |
| 身份与前端 | 成熟会话/身份协议库；已验证的 React/antd/Router/Query | 项目权限、业务页面、命令语义和五套主题 |

这不是创建一组新通用框架的任务清单。AgentDriver、Model Bridge、Tool Bridge 是现有服务中的适配模块，不新增独立部署服务；仅实现默认候选需要的接口，不先造插件市场或覆盖所有 SDK 的万能抽象。身份库及具体后端依赖在正式工程初始化时选择，不自行设计认证协议。

## 4. 当时列出的后续工作

以下顺序记录复审时的实施建议，保留作决策追溯，不表示这些事项今天仍全部未开始：

1. 按 P0-02/P0-08 建立正式后端、数据库和测试环境，继续 Phase 1 的无模型任务闭环。确定性业务操作后续由 Graph 复用。
2. 在框架依赖冻结前，做一个范围有限的 Harness 集成验证：同一个 AgentRun 实际触发压缩、回查证据、打断、恢复，并核对目标模拟服务请求数及全部模型用量。默认先验证 Deep Agents，不要求先接入所有候选。
3. 只有默认候选通过适用 H 场景后才进入真实单 Agent 集成；多 Agent、专用 coding Worker 与新工具按阶段增加。

复审当时仍待实现验证的关键项包括后端语言与精确依赖、身份提供方、出口/CNI、集群启动与隔离、完整 Harness 兼容、上游重试/计费信息、恢复/取消的实际时限。网关基础测试当时已完成，但不能替代这些检查。[实测记录](model-gateway-validation.md) 当前 Runtime、目标执行和 Harness 仍未实现；后端、身份、数据库与任务管理的后续进度见阶段验收记录。
