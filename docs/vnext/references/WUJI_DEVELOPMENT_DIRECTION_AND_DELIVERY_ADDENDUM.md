## 1. 结论：方向继续，主要调整推进方式，不重新立项

**当前没有足够依据认为开发方向存在根本性错误。建议继续这条路线，不回到 Cairn，也不再更换 Agent 底座。**

[报告事实] 新路线已经明确为 Wuji 自有 Blackboard、持久 Scheduler、Python MAF Worker、模型/工具准入和受权 React Flow 工作台。P00–P05 在各自范围 accepted；P06 仍在修复复审；P07/P13 只有局部纯函数切片；完整任务循环尚未贯通。[R1 §1、§4、§6]

[评估] 最有价值的分工已经建立：

| 当前选择 | 方向判断 | 继续落实的边界 |
|---|---|---|
| Wuji 自有黑板和 Scheduler | 保留 | 规则由 Wuji 修改，不依赖上游 Dispatcher 内部控制流 |
| MAF 负责 Agent 内部执行 | 保留 | 不自研第二套工具循环，不把 Workflow 变成第二个全局调度器 |
| ClaimRevision + FactAssessment 形成 Fact 读视图 | 保留 | Agent 可以提炼知识，但不能自行认证；不因另一文档使用 FactPublication 而重写 |
| 原始证据独立于模型最终输出 | 保留 | Worker 失败时，已采集材料仍能定位；不让抽取器成为采集前提 |
| Task/Work/Run/操作/费用分轴 | 保留 | 结果接纳不是进程退出，租约超时不是已停止 |
| React Flow 作为领域投影画布 | 保留 | 布局与领域写入分离，不在前端创建“已验证事实” |
| 单活动持久 Scheduler | 保留 | 先完成单实例可靠性和可替换策略，不抢做多主调度 |

这些选择与报告 §6 一致。[R1 §6.1–§6.8] 官方 MAF 文档也将 Harness 描述为 Agent、客户端、上下文与中间件的组合，而不是替应用提供全部业务控制面。[E1]

**主要风险不是技术选型，而是“横向基础设施越做越完整，纵向真实产品迟迟不能运行”。** P01 的 SDK 探针是必要基础，但不能代替 P07 经过实际 Gate、证据服务和控制接口的集成。该判断来自报告中的完成范围，不是对团队实现质量的推断。[R1 §5.1、§5.7]

### 1.1 三种推进方案的取舍

| 方案 | 代价 | 本次选择 |
|---|---|---|
| 重新统一为另一版 Spec，重命名并重排全工程 | 丢失已有基线，制造新迁移和重复评审 | 不采用 |
| 完全按章节串行，等 P17 才首次全面贯通 | 集成反馈过晚，运行环境与接口风险积累 | 不采用 |
| 保留 P 任务，以可运行里程碑组织小切片和并行交付 | 要明确接口所有权与切片验收边界 | **采用** |

**下一阶段应展示的是“一项真实受控工作怎样完整走过系统”，而不是新增了多少层、多少节点类型或多少证据文件。**

## 3. 哪些要坚持，哪些暂时不要扩建

### 3.1 冻结的架构边界

| 边界 | 本次明确决定 |
|---|---|
| 黑板 | 领域记录及关系的统一访问，不增加一套可独立编辑的 node/edge 真相库 |
| Fact | 允许 Agent 提出候选，不要求每个工具先实现 FactExtractor；保留核验与发布策略 |
| Scheduler | 纯排序与事务准入分离；不调用模型、不执行工具、不自增权限 |
| Supervisor | 属于 Wuji 的进程管理组件。“MAF Supervisor”是适配用途名称，不是假设 SDK 自带该产品服务 |
| 进程 | 可以继续使用独立 Python Worker 进程。要替换的是只能通过 CLI 黑盒控制的方式，不是禁止使用进程隔离 |
| MAF | 用公开接口完成模型/工具循环和上下文；不复制另一套 Agent Runtime |
| Model Gate | 做 Run 身份、当前许可、限额和调用记录；不扩建成第二个模型路由/计价平台 |
| Tool Gate | 统一注册、准入、操作身份和证据；不要为 Function/MCP 复制两套业务授权 |
| 会话 | 服务于逻辑工作，可跨兼容 Run；不是 AgentRun 的一次性附属聊天，也不是全黑板共享会话 |
| 前端 | 先实现正式画布及可用操作，再加大图优化；不采用通用流程编辑器替换领域规则 |

以上以现有报告分工为基础，Supervisor 名称与 Session 层级的澄清是本次补充，不要求为改名移动所有代码。[R1 §6]

### 3.2 暂不新增的工程范围

不新增全局 Workflow 引擎、图数据库、强制向量数据库、通用策略 DSL、多活动 Scheduler、跨框架 Session 翻译、任意后台子 Agent、第二套模型网关和工具协议框架。没有真实负载证据时，不为预计的大规模问题引入新的部署单元。

不是每个方框都要成为服务。保持现有 API/Control、Scheduler、Supervisor/Worker 和工具服务的职责即可；若拆进程确有可靠性收益，再以明确接口和故障边界拆分。

### 3.3 功能裁剪不能偷换整体目标

一个迭代只做函数工具、固定夹具或单 Worker，可以作为**封闭开发切片**；不能据此把必需的审批、恢复、正式画布和持久调度从最终验收中删除。

MCP 缺失时拒绝调用，是合法的失败路径，但不是 MCP 成功集成。先做函数工具路径有助于减少首轮变量；若已批准 Profile 必须支持 MCP，则其发布仍被实际 transport 测试阻断。报告目前仅说明缺少 `mcp.types` 时 fail closed。[R1 §8]

## 4. P06 的最小正确收口：修七项风险，不扩建平台

[报告事实] 初始候选有 3 个 P1、4 个 P2；未提交修复的聚焦测试为 21 项通过，P06 尚未 accepted。下表是关闭标准，不是对修复代码已经有效的确认。[R1 §5.6]

| ID | 问题 | 推荐处理 | 必须观察到的关闭条件 |
|---|---|---|---|
| FIX-01 | 发送前崩溃占住 inflight | 将本地执行占用、请求是否可能送出、远端结果及费用分别处理；持久化发送权移交，恢复扫描核对所有者 | 能证明没有发送权被消费的请求可按规则回收；处于“可能已发送”窗口的请求保持未知，不按 TTL 自动改成未发送或直接重试；重复恢复不重复扣减/释放 |
| FIX-02 | 取消登记后崩溃导致丢取消 | 撤销许可与待投递取消事件同事务保存；Outbox 重投相同操作身份，接收端幂等 | 在“登记后、发送前”和“发送后、回执前”分别故障；重启后旧请求仍被拒绝，取消可继续核对；不把 accepted 当 stopped |
| FIX-03 | 模型/工具数据库权限未按 purpose 隔离 | 在现有 P02 身份与角色体系内收紧授权，不另建身份系统 | 用实际非 owner 应用角色跨用途写入失败；模型 Gate 不能写工具结果，工具 Gate 不能伪造模型账本或事实评估；正常路径仍可执行 |
| FIX-04 | 合法 `tools: null` 内部异常 | 按已选协议和锁定客户端明确处理 null/省略/空数组；类型不合法走稳定错误 | 实际 ASGI→适配器链路不产生 500；未知工具与未获许可工具仍拒绝，不能为修空值关闭校验 |
| FIX-05 | 模型声明未实际装配工具 | 比较本次有效工具清单：advertised 必须是 implemented、Profile 与当前准入交集的子集 | 工具名称、版本和参数 schema 均匹配；允许按任务收缩工具集合，不要求永远宣告全部；未知工具不执行 |
| FIX-06 | 输出到上限丢失部分结果 | 在存储限额内保存已经接收的证据片段及完整性、截断原因；严格区分原字节/解码文本 | 达到边界后能读到已保存片段；不能执行半个工具调用或把截断输出当完整 JSON；未收到的总长度保持未知，不能伪造 |
| FIX-07 | OpenAPI 缺少重放响应头 | 一次修正实际响应、OpenAPI、生成 DTO 和契约测试 | 重放只返回已有记录，不触发模型或工具；敏感回包读时重新授权；规范与真实 HTTP 一致 |

### 4.1 三个不能“修快了”的细节

**未知不等于未发送。** 在持久发送标记与网络调用之间，可能存在无法确定的崩溃窗口。不能简单把所有超时 inflight 清空。模型调用的纯费用待核对也不应无条件阻塞整个 Task；能否继续，按受影响工作、资源和冻结预算策略决定。

**局部资源释放不等于远端业务已停止。** 确认本地连接/进程已退出后可以释放相应本地槽位，但未决费用和未知外部操作仍需保留。资源冲突范围不清楚时再扩大冻结，不能默认复用。

**工具清单包含 Harness 自带能力。** Todo、受限记忆工具也要出现在明确的工具清单和政策中，不能被误当成非法工具，也不能因名称前缀就自动放行。若它们在本地执行，必须有已登记的执行位置和同等准入/审计规则；不得静默绕过现有 ToolAdmission。首个切片可以关闭未接好的可选能力，但不能声称已验证全部 Harness 功能。

### 4.2 P06 的回归范围

除 `tests/vnext/test_run_admission.py` 外，至少补充受影响的 P02 身份/RLS、P03 采集/证据、P04 评估写权限、P05 撤销/容量回归。使用实际数据库角色与独立连接，不用测试 fixture 直接返回业务结论。

报告已有两条命令可继续使用，执行前确认活动工作树脚本存在：

```bash
./scripts/vnext/uv.sh run --frozen pytest tests/vnext/test_run_admission.py -q
work/toolchain/bin/pnpm contracts:check:v2
```

这两条命令不代表完整回归范围。由现有 AC→test 映射选择受影响测试，保留确切命令和结果；不要凭猜测添加不存在的 test 路径。

### 4.3 收口后不要继续无界追加 Gate 功能

七项发现关闭、必要回归完成且合同可交接后，固定一个被测候选，推进 Worker 集成。全协议网关、通用代理插件和新计费策略不属于这个收口任务。

`AgentPayload` 未引用警告须核对用途：若为唯一结果载荷合同，将其绑定实际请求 schema；若是废弃组件则经合同负责人移除；若由非 HTTP 入口使用，登记真实消费者及测试。不能仅为消除 lint 警告编造一个无业务用途的 HTTP 端点。[R1 §5.6]

## 5. 在更多模块开工前，先冻结六份跨模块交接

这不是增加六套框架。复用现有类型和命名，补齐字段含义、所有者与验收。能映射到已有合同的，不新增平行 DTO。

| 交接 | 所有者 → 消费者 | 必须明确的语义 |
|---|---|---|
| 工作与运行身份 | P05/P09 → P06/P07/P10 | Task/WorkItem/Run 身份、执行代次、许可、环境、限额；身份从认证上下文取得，不信任模型自填 |
| 有效工具清单 | P06/P07 共同，合同负责人合入 | 声明工具、实际装配、schema/version、执行位置和当前许可；包含受控的局部 Harness 工具 |
| 调用与证据回执 | P06/P03 → P07/P08/P11 | 稳定操作身份、真实 attempt、发送/完成/未知、完整性、受权证据引用；模型原生 call ID 按 opaque string 保存 |
| Session 与操作前沿 | P08 定义，P06/P07/P10 提供事实 | 消息/state/记忆的同版 manifest；检查点之后有哪些真实操作，不只检查文件是否完整 |
| 启动/停止/退出回执 | P10 → P05/P09/P11 | 相同 operation ID 不重复启动；真实进程身份及退出证明；未知状态不能释放冲突资源 |
| 受权图与布局 | P13 → P14/P15 | 版本化节点/边、视图游标、权限域、快照边界；布局只允许坐标/视口等展示字段 |

### 5.1 Session 归属明确到逻辑工作

报告中的 `Task → IntentRevision → WorkItem → AgentRun → Session` 是简图，不宜直接据此建立强制的一对一外键链。[R1 §6.3]

[核验要求]

- Explore WorkItem 关联固定 IntentRevision；Reason 工作关联 Task、触发代次和快照，不必伪造 Explore Intent。
- Session 归属于逻辑工作；多个兼容 Run 可依次使用同一 Session，不并发写。
- 新 Run 不重置预算、尝试额度、工具操作身份或用户 hold。
- 若现有实现已满足，只补文档，不迁移数据库。

### 5.2 恢复的关键交接：操作前沿

将“检查点之后的工具/模型操作位置及身份集合”定义成恢复比较合同。可采用 `operation_frontier` 名称，也可映射本地等价结构；不强制改名。

| 场景 | 决策 |
|---|---|
| 检查点完整，之后没有动作，环境与许可兼容 | 可从已验证边界续接 |
| 工具已完成，结果未进入检查点，但原回执完整且 SDK 支持关联恢复 | 回送原结果，不重新执行工具 |
| 已结算但 SDK 无法安全接回原会话 | 按事先发布的恢复政策，从已接纳知识建立明确的新上下文；显示不是无损恢复 |
| 工具是否执行未知 | 核对并冻结冲突工作，禁止盲目再发 |
| 环境、参数、授权或审批已变更 | 原续接资格重新判断；不以旧批准恢复新动作 |

多个条件必须同时满足，不把“Session 能反序列化”当成恢复通过。公开 SDK 的组合和恢复行为以 P01/P07/P08 对冻结版本的实测为准；官方文档不能替代本地锁定发行物证据。[R1 §5.1、§6.6；E1]

## 6. 新的推进方式：P 任务不变，增加可运行里程碑

M0–M5 是交付检查点，不是新的产品状态、不是重编号，也不是替代原 75 项 AC。一个 P 可先交局部切片，再完成全部验收；必须分别记账。

### M0：可继续集成的基线

**覆盖：**P00/P02 的基线索引，P06 修复复审；环境检查并行。

**产出：**可定位的 P06 修复候选、七项发现关闭记录、受影响回归、六份交接的最小版本。

**同步处理：**确认允许的本地 Docker/Kubernetes 开发环境能否启动。报告中的不可用状态应被尽早核对，不等到 P10 才发现。仅使用项目现有开发环境脚本；系统服务启动、配置变更按原批准执行，不升级为生产操作。[R1 §8]

**退出：**安全与持久化问题有实际关闭证据；合同可被消费。截图和汇总格式的补齐不阻塞无关纯函数开发，但不可以省略真实测试。

### M1：真实 MAF 的单工作开发闭环

**覆盖：**P07 的第一集成切片，复用 P03/P04/P05/P06，并使用 P01 已建立的本地合成上游。

**目标路径：**

```text
受权的固定工作输入
→ 实际 MAF Worker
→ 实际 Model Gate
→ 本地合成模型端点
→ 实际函数工具 / ToolAdmission
→ 读取固定无害文件
→ 实际 Evidence Capture / Observation
→ 返回原工具结果给 MAF
→ Agent 提出 Claim
→ 原始结果与候选接纳
```

**不等待完整 Scheduler、Kubernetes 调度或图画布。** 测试宿主可以承载真实 Worker，测试数据可准备受权 WorkItem；必须使用实际准入、证据、接纳服务，不能添加产品可用的绕过 Gate 的启动入口。

该切片不冒称 P10 完成：测试父进程可以真实观察子进程退出，但不得伪造生产 Supervisor 回执，不将手工 fixture 派发算成持久 Scheduler 验收。缺少生命周期能力时保留正确中间态，不为了演示成功直接改 Task 为 completed。 自动恢复尚未完成时保持禁用；崩溃后进入明确的待核对状态，不由测试入口自动重启旧工作。

**至少验证：**工具请求真实发生、证据可读、Claim 来源正确、Fact 未自动发布、撤销后新动作被拒、原结果重放不再调用工具。合成模型只证明协议机制，不证明自主推理效果。

**退出：**有一个可重复运行的实际单工作闭环，所有未完成的恢复/调度能力仍明确标记；P07 其余 AC 继续保留。

### M2：持久派发与进程管理闭环

**覆盖：**P09 最小策略/事务派发 + P10 启动/停止/回执，接入 M1；P08 可以同步开发和探测。

**目标：**同一条工作不再由测试手工派发，而是由真实持久 Scheduler 领取，经 Outbox、Supervisor 启动同一个 Worker 实现。测试入口不发展成第二套调度器。

**策略先简单：**使用现有已批准的排序和容量规则；没有必要在第一轮编写自学习优先级、复杂策略评分或动态角色系统。策略代码与事务领取分离。

**退出：**相同启动身份重投不双 spawn；进程未退出不释放槽；控制服务或调度器重启不丢工作；并发领取保持唯一有效持有者。Docker/Kubernetes 的专属验收在真实目标部署拓扑执行，本地宿主通过不能替代。

### M3：恢复、人工输入和结束能正确协作

**覆盖：**P08/P11/P12 的完整集成，并回归 P05/P06/P09/P10。

**目标：**审批、普通输入、用户 hold、Task pause、会话续接、完成预检查和有限收敛在同一真实路径上成立。

必须覆盖旧完整检查点之后已执行工具、暂停叠加、批准后撤销、多项待批、Reason wait 释放位置、完成期间出现新反证等场景。等待与唤醒不能丢失事件；恢复不能制造新操作额度。

ReportCommit 先冻结依据，渲染作为后续交付动作；渲染失败不重新启动探索。费用待对账、工具执行未知、本地进程已退出是不同状态，不合成一个模糊 success。

**退出：**能证明“会运行、能停止、不会错误重跑、不会错误宣布完成”。不因某项必需 SDK 能力难实现就删掉原 AC；明确失败范围，继续不依赖该能力的开发。

### M4：受权工作台闭环

**覆盖：**P13/P14/P15，以及 P16 中与公开输出直接相关的能力。它是一条与 M1–M3 并行准备、最后汇合的工作线。

- P14 的正式 `TopologyFlowCanvas` 可先消费固定、已冻结 DTO，完成节点/边、布局、选择、详情和可访问性纯展示。
- P13 在共享 schema/权限合同稳定且迁移所有权可安排后，建立真实快照、分页和受权 API，不以全 P06 收口作为纯展示代码的前提。
- P15 再接入真实控制、事件流、权限变化和历史模式。
- 第一个受权页面可先用既有快照 API 刷新形成内部演示；这不替代正式 ViewStream，也不允许把尚未通过的实时语义标为发布能力。

**退出：**能够看见真实工作状态、定位 Claim 到证据、操作允许的 hold/审批；拖拽不写领域状态，权限失效阻断后续读取，历史不执行动作。五主题、键盘与列表替代保留最终验收。

### M5：统一验收、归档和新发布物

**覆盖：**P16 剩余治理、P17 全部核心验收、P19 一致归档、P20 干净发布；P18 评测基础设施提前准备，效果试验单独授权。

**M5 不能只依赖后端 P12。** P17 的最终通过必须覆盖活动计划中原本要求的 P15/P16 和全部必需能力；各 P 局部证据不能拼接冒充同一集成版本的端到端通过。

P19 可提前做旧数据清单和只读样本解析，但真实一致导出、受权读取、存储保留和切换演练仍要在相关模块可用后完成。最终新运行/查询不依赖 Cairn/Pi，历史材料不必删除。

**退出：**新版本可在干净环境启动并读取合法历史，统一 AC 有真实结果；尚未授权的费用试验、外部目标、停机切换或数据删除保持未执行。不得用“已构建镜像”替代用户批准切换。

### 6.1 并行关系摘要

```text
M0：P06修复 + 接口交接 + 开发环境核对
  ├─ M1：P07真实单工作闭环
  │      └─ M2：P09 / P10持久派发与进程管理
  │                └─ M3：P08 / P11 / P12恢复与完成
  ├─ 展示线：P14固定DTO + P13持久投影 → P15真实联调 → M4
  ├─ P16最低限度审计/脱敏从入口开始，完整治理在M5前收口
  └─ P18评测数据格式、P19只读归档清单可提前准备

M3 + M4 + 完整P16 → P17统一验收
P17 + 完整P19    → P20发布物 / 独立批准的切换
```

P08 的设计与 SDK 测试不必等 M2 完成；完整恢复验收需要 M2 的真实账本与进程事实。这种“先准备、后集成”的区分同样适用于 P13–P16。

## 8. 有序开发：控制共享文件，不把模块门禁扩成全局封锁

### 8.1 一个集成负责人，按边界分工作线

| 工作线 | 可同时开展的范围 | 不可独占修改的共享面 |
|---|---|---|
| 核心集成负责人 | P06收口、合同/迁移整合、发布索引 | OpenAPI、生成DTO、共同状态枚举、数据库角色、根锁文件 |
| Worker/恢复线 | P07、P08及其与P06/P10的端口 | 不自行改Gate wire schema或核心权限 |
| 调度/运行线 | P09、P10和P11控制接入 | 不自行改变知识评估、Session格式 |
| 工作台线 | P13/P14/P15，先做固定DTO展示 | 不修改后端真相或构造演示成功状态 |
| 治理/评测辅助 | P16基础、P18数据格式、P19只读清单 | 不调用收费模型，不接管生产环境 |

上表不是要求同时启动五个 Agent。资源有限时按主线串行执行；只有接口稳定、文件不冲突时才并行。优先保持一个核心集成点和少数独立工作线，避免为了并行增加协调成本。

### 8.2 迁移和合同的合入规则

- 共享合同变更先写意图、兼容影响和正反示例，再由负责人统一生成 DTO；消费者不手改生成文件。
- 数据库迁移编号从集成分支真实 head 分配；并行草稿不抢号、不用私自修改公共 head 解决冲突。
- 已 accepted 的旧迁移不为“整理历史”而重写；新的修复用符合项目迁移规范的增量处理。
- 纯函数/UI 切片可针对冻结版本继续开发；只有消费已改变字段、数据库角色或状态含义的集成才等待对应 Gate。
- 每条工作线合入后，触发按依赖影响选择的回归；P17 再运行统一矩阵。

### 8.3 红灯只阻塞受影响路径

| 未关闭项 | 必须暂停 | 仍可继续 |
|---|---|---|
| P06权限/未知操作/取消修复 | 依赖该路径的实际模型或工具集成、发布 | 纯ContextBundle、固定DTO画布、评测格式、文档核对 |
| OpenAPI共享字段未定 | 依赖该字段的生产端口接入 | 不消费该字段的独立逻辑 |
| Docker/Kubernetes不可用 | 该拓扑下的Supervisor和发布验收 | 本地SDK、真实PG、函数工具和组件测试 |
| MCP依赖不完整 | MCP工具Profile发布 | 已批准且不需要MCP的函数工具切片 |
| 截图或汇总模板未整理 | 受现行交付格式约束的最终验收签字 | 原始结果已固定的无关后续开发；不得丢证据 |
| 跨租户可见性未验证 | 接入真实敏感数据和对应公开工作台发布 | 无敏感固定fixture的纯组件开发 |

没有测试证据的安全问题不得以“赶进度”豁免。反过来，也不要让纯格式整理或无关可选 transport 成为所有模块的全局锁。

### 8.4 环境与备份提前处理

P00 时不可用的 Docker daemon 是依赖风险，不是架构错误。[R1 §8] 现在核对本地环境、实际版本、资源占用、可用启动脚本和权限；不得依赖后续“总会恢复”。

当前分支没有 upstream，P06还有未提交修改。[R1 §2] 先保护本地工作。单独记录“代码已备份”和“代码已推送”；没有用户批准不自动推送、发布、删除目录或数据卷。

## 9. 测试与证据：按风险匹配，不用材料数量管理进度

### 9.1 四层测试，不互相冒充

| 层 | 应真实运行什么 | 可以替换的边界 | 不能证明什么 |
|---|---|---|---|
| 纯规则/组件 | 上下文、排序、投影、布局与文本显示代码 | 明确固定DTO/记录 | 不能证明RLS、网络或SDK集成 |
| 组件集成 | 实际ASGI、真实PG应用角色、实际采集/接纳 | 受控外部模型响应或只读fixture | 不能证明Scheduler/Supervisor全链路 |
| 运行闭环 | 实际MAF、Gate、调度、Supervisor及工作台 | 明确标记的合成模型、封闭夹具 | 不能证明真实模型效果和生产隔离 |
| 效果/部署 | 获准的真实模型任务或真实部署拓扑 | 按单独方案冻结 | 不能由文档或旧W1结果继承通过 |

### 9.2 下一轮集成必须看的八个场景

这些是场景描述，不是新 AC 编号；映射到现有75项，缺项由决定记录正式补充。

| 场景 | 关键断言 | 主要负责 |
|---|---|---|
| 无抽取器的工具往返 | Observation可用，Agent可提Claim，Fact不自动认证 | P03/P04/P07 |
| 非结构化候选经人审/规则核验 | 保留同一ClaimRevision和来源，缺解析器不阻断正当核验 | P04 |
| 结果重投 | 返回原回执，不新增工具执行和Claim版本 | P06/P07/P11 |
| 暂停与局部hold叠加 | Task恢复不解除用户hold；无关工作不被错误撤销 | P05/P10/P11 |
| 检查点后工具已完成 | 恢复核对原操作前沿，不重放副作用 | P06/P08/P10/P11 |
| Reason等待与先到事件 | 条件先发生仍能唤醒；Reason结算后不占唯一位置 | P09/P11 |
| 完成提案遇新反证 | 不错误完成，不无限等待被禁止的新调用 | P12 |
| 图快照与权限变化 | 不混latest，不泄漏隐藏事件序号，旧响应不覆盖撤权状态 | P13/P15 |

### 9.3 证据最小集

每个可评审候选保存一份索引：源代码/工作树摘要、锁文件/迁移版本、测试清单、实际命令、退出码、结果文件、发现关闭记录与未测范围。原始日志按需保存，敏感内容进入受限目录。

**纯函数不要求伪造 HTTP 或终端截图。** HTTP 组件保留脱敏的真实请求/响应，UI 组件保留实际浏览器操作与必要截图，数据库并发用真实事务与状态读回，SDK 用真实请求/工具事件。安全问题的复现材料必须能够支持对应结论。

若当前活动 DeliveryProfile 确实要求“每项都截图＋HTTP”，先由集成负责人在既有决定记录中区分“开发验收证据”和“客户成果报告”。工程证据采用按媒介策略；客户交付合同不得被静默删除。报告本身将纯函数切片缺少 HTTP/UI 材料列为不完整原因，本次只纠正证据媒介与行为范围混淆。[R1 §5.7]

### 9.4 候选版本与证据不要互相污染

测试绑定代码候选和执行时工作树摘要；后续仅添加报告或截图可以形成证据提交，但应保留真正被测代码身份。若测试后又改了业务代码、合同、迁移或依赖，则重跑受影响测试，不能沿用上一份通过结果。

## 12. 本补充如何验收，以及什么情况下才重新讨论架构

### 12.1 补充方案的完成标准

- 当前活动基线可唯一定位；不出现另一个同名v2覆盖当前合同。
- P06 七项风险有实际关闭结果或清晰保留的阻断项，而非仅21项测试总数。
- M1比“完整系统全部做完”更早发生；真实 SDK 已经过实际 Gate 和证据/候选接口。
- 至少一条不依赖 P06 运行修复的展示/纯逻辑工作可以独立推进，权限问题没有被豁免。
- 进度按可运行里程碑、原 P/AC 与未测边界汇报，不按文件数和线性任务百分比汇报。
- M5包含原计划要求的前端、治理、归档及统一故障验收；没有缩减最终范围来伪造完成。

### 12.2 只有具体证据才触发结构性重议

以下情况可以提出一项独立变更决定：锁定 MAF 公开接口无法满足必需恢复/审批合同；现有Gate协议无法表达合法模型请求；数据库短事务成为经测量的瓶颈；实际部署拓扑无法满足已批准隔离边界；真实对照显示协调成本长期大于收益。

应提交最小失败复现、影响Profile、保持现有语义的可选修复与代价，再讨论是否需要结构调整。不要因为单个可选功能未支持、某个状态名不同、图不够漂亮或“以后可能会扩大”就启动新一轮重构。

**总指令：沿当前路线推进；保留已完成成果；以真实闭环和故障证据指导优化，而不是再靠一份更大的架构图推进开发。**
